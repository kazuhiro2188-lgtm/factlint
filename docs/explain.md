# 仕組みの解説

> このツールが何をしているかを、コードを開かずに理解できるように書いた文書。
> 設計判断の「なぜ」は [ADR](adr/) に、「何を作るか」は [仕様書](spec.md) にある。

## 1. 全体の流れ

やっていることは4段階しかない。

```
① AI生成文から数値を取り出す        extract.ts
② ソース（入力データ）から数値を集める  source.ts
③ ソースの値から計算できる候補を作る   derive.ts
④ ①と②③を突き合わせる             match.ts / check.ts
```

具体例で追う。

```
ソース: { "assets": 152800, "liabilities": 167400 }
出力文: 「充足率は 91.3% です」
```

| 段階 | 起きること |
|---|---|
| ① | `91.3%` を取り出す。値 91.3 / 単位 percent / **小数1桁** と記録する |
| ② | ソースから 152800（ラベル assets）と 167400（ラベル liabilities）を集める |
| ③ | 2値の演算を並べる。その中に `152800 ÷ 167400 × 100 = 91.2784...` がある |
| ④ | 91.2784... を**小数1桁に丸めると 91.3**。①と一致 → 根拠あり（derived） |

判定は「値が等しいか」ではなく、**「その桁数で書いたら同じ表記になるか」**を見ている。これが丸めを正しく扱えている理由。

## 2. ファイルごとの役割

### `packages/core` — 判定エンジン（実行時依存ゼロ）

| ファイル | 役割 |
|---|---|
| `types.ts` | 型定義だけ。処理は書かない |
| `extract.ts` | 文章から数値を取り出す。除外ルール（西暦・日付・バージョン・箇条書き番号）もここ |
| `source.ts` | 入力データを再帰的に辿って数値を集める。JSONでも素のテキストでも受ける |
| `derive.ts` | 計算候補を作る。根拠が見つからないときは「最も近い候補」を返す |
| `match.ts` | 丸めて比較する。ここだけ数学的に神経を使っている |
| `check.ts` | 上を順に呼んで結果をまとめる |

### `packages/cli` — コマンドライン

| ファイル | 役割 |
|---|---|
| `args.ts` | 引数の解釈だけ。副作用なし＝テストしやすい |
| `render.ts` | 結果の表示。human / json / github の3形式 |
| `index.ts` | ファイル読み込みと組み立て |
| `bin.ts` | 実行ファイルの入口。ここには判断を書かない |

### `apps/demo` — ブラウザデモ

エンジンをそのまま `import` している。ビルド工程はコピーだけ（`scripts/build-demo.mjs`）。
**依存ライブラリが無いのでバンドラが要らない** ——「実行時依存ゼロ」が単なる自慢ではなく実利になっている例。

## 3. 説明できるようにしておきたい設計判断

### 判断1: 検証にAIを使わない

「AIの幻覚をAIで検出する」と、検証結果が毎回変わる。CIの合否判定に使えない。さらに**検証側が誤判定しても気づけない**。
そこで対象を数値に絞り、決定論的に解いた。狭いが、確実で、判定ロジック自体をテストできる。

> 聞かれたら: 「検証する仕組み自体が検証できないなら、それはゲートとして機能しません。だから範囲を狭めました」

### 判断2: 派生値（計算で導ける値）を根拠として認める

AIは与えられた数値をそのまま書くだけでなく、合計や比率を**計算して**書く。単純な照合だと正しい文章まで誤検知する。
誤検知が続けばツールは回避され、回避されたゲートは無いのと同じ。だから合計・平均・差分・比率を追えるようにした。

> 聞かれたら: 「誤検知でツールが捨てられるほうが、見逃しより損失が大きいと判断しました」

### 判断3: 無関係な2値は掛け合わせない

**これは実際に事故ってから入れた対策**。最初の実装では、あるポジションの元本（20,100）を全体の負債（167,400）で割った意味のない計算が 12.01 になり、根拠のない「12%」を通してしまった。

対策として、2値演算を許す組み合わせを次のどちらかに限定した。

- **同じまとまりの中の値どうし**（同じ行の 回収額 ÷ 元本）
- **同じ項目名の値どうし**（各行の 元本 の合計）

この事故は回帰テストとして残してある（`check.test.ts` の最後の describe）。

> 聞かれたら: 「初回に自分のデータで試したら偽陽性が出たので、意味のある組み合わせだけに絞りました。同じ事故が再発しないようテストにしています」

### 判断4: 根拠が無いときは「最も近い候補」を出す

`ungrounded` とだけ言われても、利用者は次に何をすべきか分からない。
最も近い候補を差分つきで出すと、「プロンプトの問題（本当に幻覚）」なのか「入力データが足りないだけ」なのかが1秒で分かる。打つ手がまったく違う。

### 判断5: 諦めたときは黙らない

ソースの数値が多すぎると2値演算を打ち切る（既定80件）。このとき結果に `truncated: true` を立て、画面にも警告を出す。
**精度を黙って落とすと、利用者は落ちたことに気づけない。**

## 4. 想定問答

**Q. 正規表現で数値を拾っているだけでは？**
数値の取り出しはそうです。本体は取り出したあとの照合ロジックで、丸めの許容幅の決め方と、派生値の探索がここにあります。単純な文字列一致なら10行で書けますが、それだと実用になりません。

**Q. 除外ルールはなぜ必要？**
「2026年」を根拠のない数値として報告すると、利用者は初日で使うのをやめます。誤検知はゼロにできませんが、明らかに数値でないものは既定で外しています。設定で戻せます。

**Q. 派生値の探索は全探索ですか？**
いいえ。演算を意図的に絞っています。任意の四則演算を深さ2〜3で全探索すると、どんな数値にも「たまたま一致する候補」が見つかり、根拠なしを検出できなくなります。探索を広げるほど検出力が落ちる、というのがこのツールの肝です。

**Q. 見逃しはありますか？**
あります。候補が増えるほど偶然の一致は起きます。ADR-0002 にトレードオフとして明記しています。誤検知でツールが捨てられるより、見逃しのほうがましだという判断です。

**Q. 日本語以外でも動きますか？**
数値の取り出しは英語表記（`about`, `approximately`, `$`）にも対応しています。単位の語彙は日本語中心です。

**Q. なぜ依存ライブラリがゼロ？**
検証ツール自身が依存を持つと、その依存の更新で結果が変わりえます。またブラウザでバンドラなしに動かせるのは実利です。デモページが実際にそうなっています。

**Q. 大きなデータでも動きますか？**
2値演算はソース値の件数の2乗に比例します。既定では80件を超えたら打ち切り、集約のみで判定して、打ち切ったことを結果に明示します。

**Q. テストは何を担保していますか？**
82件のテストが、数値の取り出し・除外ルール・丸め・派生値の判定・根拠なしの検出・打ち切りの申告を押さえています。加えてCIで、根拠のある文章が成功で終わり、根拠のない数値を含む文章が失敗で終わることを毎回確かめています。

**Q. LLM-as-a-judge と併用できますか？**
できますし、そのほうが良いです。数値は factlint が決定論的に、文章表現はLLMで、と分担すれば競合しません。

**Q. 実務ではどこに置きますか？**
AI生成の結果を利用者に返す直前、または配信バッチの中です。根拠なしが出たら配信を止めて人にエスカレーションする、という使い方を想定しています。
